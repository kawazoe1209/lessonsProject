オリエンティッド・ダイレクティッド ◎/○/? 記入 「〜指向」と「有向」は対義語に見えて実は答えている問いが違う──プロダクト設計を語る2つの軸を混同しないための語彙整理

概要

「オリエンティッド(-oriented/指向)」と「ダイレクティッド(directed/有向)」は、どちらもプロダクトや設計の性質を形容する言葉だが、答えている問いが違う。「〜指向」はシステムが何を中心に組み立てられているかという“レンズ”を指す接尾辞で、オブジェクト指向(1960年代のSimulaに始まりSmalltalk・C++で定着)、データ指向設計(ゲーム開発で普及、CPUキャッシュ効率を優先しクラス階層より配列的なデータレイアウトを重視する)、目標指向(ゲームAIのGOAP=Goal-Oriented Action Planningのようにゴールから逆算して行動を選ぶ設計)のように、「何を判断基準の中心に置くか」を宣言する。

一方「有向」は、要素間に明示的な順序や向きがあるかどうかを指す言葉。有向グラフ(directed graph)は矢印で依存や遷移の向きを持つグラフで、Gitのコミット履歴やMakeの依存解決、Airflow・GitHub ActionsのようなCI/CDパイプラインはすべてDAG(有向非巡回グラフ)としてモデル化される。ここでの「向き」は「これが終わったら次はこれ」という実行順序の話で、「何を目的に据えるか」という指向とは軸が違う。最初は対義語かと思いがちだが実際には両立する概念で、「ユーザー指向だが道筋は決め打ちの有向なロードマップ」も「データ指向だが分岐が多く非決定的な設計」もあり得る。プロダクト設計を語るときはこの2軸を分けて問うと輪郭がはっきりする。

リモート認証 ◎/○/? 記入 指紋やFace IDでログインする裏側では、パスワードそのものが存在しない──秘密鍵を一切外に出さずに「本人であること」を証明する仕組み

概要

WebAuthn(パスキーはその一般向けの呼び名)は、パスワードを一切使わずにログインするための仕組み。最初にサイトへ登録するとき、手元の端末(スマホやPC)が内部で「鍵のペア」を1組作る。片方は端末の中(指紋センサーやFace IDで保護された領域)に閉じ込められたまま外に出ない秘密鍵、もう片方はサーバーに送って保存してもらう公開鍵。パスワードのようにサーバーへ送って照合される秘密の文字列がそもそも存在しないので、サーバーがハッキングされて情報が漏れても、盗まれるのは公開鍵だけで悪用のしようがない。

ログインするときの流れはこうだ。①サーバーが「これに答えて」とランダムな乱数(チャレンジ)を送る。②端末は指紋やFace ID、PINでロックを解いて、端末内に眠っている秘密鍵でその乱数に署名する(秘密鍵自体はここでも一歩も外に出ない)。③その署名だけをサーバーに送り返し、サーバーは事前に預かっていた公開鍵で「確かにこの秘密鍵の持ち主が答えた」と検証する。指紋やFace IDは「本人確認のスイッチを入れる手段」であって、指紋データ自体がネットワークを流れるわけではない点も誤解されやすいポイント。また鍵はログインするサイトのドメインごとに別々に作られるため、そっくりな偽サイトを踏んでも、端末側がそもそも「このサイト用の鍵は持っていない」と判断して差し出さない。

proxyman ◎/○/? 記入 アプリの通信を丸裸にして、バックエンドが無くてもフロントを作り、エラー画面も人工的に再現できる──開発を先に進めるためのプロキシツール

概要

Proxymanはアプリ(スマホアプリやブラウザ)とサーバーの間に割り込んで、そこを流れる通信をそのまま見えるようにするツール。ローカルにルート証明書をインストールしておくことでHTTPS通信も復号して表示でき、「このアプリはどんなヘッダーを付けてリクエストしているか」「サーバーは実際どんなJSONを返しているか」を、コードを一切書かずに画面上で確認できる。iOS/Androidのシミュレータはもちろん、実機の通信もWi-Fi経由でプロキシを通せば同様に覗ける。

単に「見る」だけでなく、通信そのものを差し替えて開発を前に進められるのが実用上の価値。Map Local機能を使うと、サーバーからの実際のレスポンスをローカルのJSONファイルに置き換えられるため、バックエンドAPIがまだ完成していなくても「こう返ってくるはず」という値を仮置きしてフロント側のUIを先に作れる。Map Remoteはリクエストの向き先自体を別サーバー(たとえば手元のローカル開発サーバー)に切り替える機能。Breakpointを使えばリクエストやレスポンスをその場で書き換えて送受信できるので、通常操作では再現しにくいエラーレスポンスやタイムアウトを人工的に発生させ、アプリ側のエラーハンドリングを確認する、といった使い方もできる。サードパーティSDKが裏で何を送信しているかを覗いて、意図しないデータ送信がないか確かめる用途でも使われる。

デプロイ ◎/○/? 記入 「ファイルをサーバーに置いた」だけでは終わらない──ローカル・ステージング・本番で変わる「デプロイ完了」の基準

概要

「デプロイ」は一語で語られがちだが、実際には ビルド(ソースを実行可能な成果物にする) → 設定注入(環境変数・シークレット・接続先を対象環境用に切り替える) → 転送(コンテナイメージのpush、静的ファイルのアップロード、コードのsshなど) → 起動(プロセスやコンテナを立ち上げる) → 疎通(ヘルスチェックが通り、ロードバランサやDNSが新バージョンにトラフィックを向ける)という複数ステップの合成語。「ファイルがサーバーに置かれた」だけではデプロイ完了とは言えず、プロセスが実際に起動しヘルスチェックに応答し、かつ外部からのリクエストがそのバージョンに届いて初めて完了と呼べる。

この「完了」の基準は環境によって変わる。ローカル環境への「デプロイ」は多くの場合、ビルド〜起動までを自分のマシン上で完結させる作業で、本番同様のDockerイメージを docker compose up で立てたり .env.local で本番相当の設定を模したりする程度にとどまり、DNS切り替えやロードバランサへの登録といった疎通ステップは省略・簡略化される(localhostへの疎通は最初から成立しているため)。ステージング環境は本番と同じインフラ構成・デプロイ手順を使いつつ設定だけ切り替える「本番のリハーサル」で、QAや結合テストのゲートになる。本番環境ではさらにダウンタイムをどう扱うか(Blue-Green・Canary・Rolling Update)、失敗時にどう即座に戻すか(ロールバック)、デプロイ後の監視(エラー率・レイテンシのダッシュボード)までが「デプロイ」の責任範囲に含まれることが多く、環境が上がるほど「完了」の定義は「動いた」から「安全に切り替わり続けている」へと重くなっていく。

CBOR・COSE ◎/○/? 記入 JSONを小さくしたCBOR、それに署名と暗号化を足すCOSE──WebAuthnの裏側で認証と静かにつながっている低レイヤー標準

概要

CBOR(Concise Binary Object Representation、RFC 8949)はJSONと同じデータモデル(マップ・配列・文字列・数値など)を、より小さく高速にパースできるバイナリ形式に落とし込んだもの。同じデータをJSONとCBORで並べると差がわかりやすい。

// JSON(17バイト)
{"a":1,"b":"hi"}

// 同じ内容をCBORで表すと、9バイトの16進列になる
A2 61 61 01 61 62 62 68 69
  A2       → 要素数2の「マップ」であることを示す
  61 61    → 長さ1の文字列 "a"
  01       → 数値 1
  61 62    → 長さ1の文字列 "b"
  62 68 69 → 長さ2の文字列 "hi"

クォートやコロン、カンマといった区切り文字を排除し、値の型と長さを1バイトのヘッダーに埋め込むことでサイズを落としている。整数やバイト列を可変長で詰め込めるほか、タグを使って日時やbignumのようなJSONにない型も表現できる自己記述的なフォーマットで、帯域や処理能力が厳しいIoT機器・組み込み向けに設計された。実際にはWebAuthnの認証器が返す attestationObject の実体がCBORであるなど、Web標準の内部フォーマットとしても使われている。

COSE(CBOR Object Signing and Encryption、RFC 9052/9053)はCBORデータに署名・暗号化・MACを付与する仕組みで、JOSE(JWS/JWE/JWK)のCBOR版に相当する。署名付きメッセージ(COSE_Sign1)は、実体はCBORの配列だが、JSON風に書くとこういう4要素になる。

// COSE_Sign1 のイメージ(中身は本来CBORバイト列)
[
  { "1": -7 },              // 保護ヘッダー: alg = -7 (ES256)
  {},                       // 非保護ヘッダー
  "7b2261223a312c2262223a...",  // ペイロード(バイト列)
  "3045022100d7d1a...b3f"       // 署名(バイト列)
]

JWTなら {"alg":"ES256"} と文字列で書くヘッダーを、COSEでは {1: -7} のようにキーも値も数値コードにして詰め込むため、この時点でさらに縮む。CWT(CBOR Web Token、RFC 8392)はこの仕組みでJWTに相当するトークンを組んだもの。実利用例として、ISO 18013-5で標準化されたモバイル運転免許証(mDL、Apple/Google Walletの運転免許証機能の裏側)やWebAuthnの署名検証にCOSEが使われており、前項の「リモート認証」(WebAuthn/パスキー)とはワイヤーフォーマットの層で直接つながっている。導入時はJSON運用に慣れたチームがバイナリのデバッグしにくさと鍵管理の実装コストを負う点が実務上のハードルになる。
